# Findings

Все утверждения разделяются по источнику подтверждения.

## Подтверждено исходным кодом

- NMS.py `master` на commit `fc175d475ed2f83a1e77806a50bceb5380744f3f`
  имеет версию пакета `178994.0`.
- NMS.py зависит от `pymhf[http_api,gui]==0.2.4`.
- Официальный README сообщает, что Python 3.14 пока не поддерживается.
- `cGcDiscoveryData.mUniverseAddress` объявлен по offset `0x0`.
- `cGcDiscoveryData.meType` объявлен по offset `0x40`.
- `cGcDiscoveryType`: `Animal = 3`, `Flora = 4`, `Mineral = 5`.
- Объявления `PopulateDiscoveryInfo` и `SubmitDiscoveryData` существуют.
- `cGcDiscoveryManager::SubmitDiscoveryData` присутствует в актуальном
  `broken_patterns.txt`.

## Подтверждено локальной статической проверкой

- Платформа: Steam.
- `NMS.exe`: `<game folder>\Binaries\NMS.exe`.
- Версия файла: `178938`.
- Steam build ID: `25233815`.
- Официальная сигнатура `PopulateDiscoveryInfo` имеет одно совпадение в `NMS.exe`.
- Официальная сигнатура `SubmitDiscoveryData` не имеет совпадений в `NMS.exe`.
- Системный Python 3.14.2 x64 оставлен без изменений. Дополнительно, отдельно и
  без изменения `PATH`, установлен Python 3.13.15 x64; проектное `.venv`
  содержит `nmspy 178994.0` и `pymhf 0.2.4`.
- Пользователь подтвердил создание ручной резервной копии сохранения.
- Ghidra 12.1.3 нашла `PopulateDiscoveryInfo` по VA `0x1412AD700`
  (file offset `0x12ACB00`) и подтвердила шесть аргументов.
- Внутри неё прямой вызов по VA `0x14044EB60` получает пять аргументов и
  возвращает `bool`. Его уникальная сигнатура имеет одно совпадение по file
  offset `0x44DF60`.
- Первый аргумент вызова — глобальный discovery-manager, второй — указатель на
  discovery data, третий берётся из `_time64(nullptr)`, четвёртый является
  допускающим null указателем на однобайтовый флаг, пятый — однобайтовый флаг.
- В кандидат-функции значение по `discovery_data + 0x0` участвует в проверке
  universe/portal address, а enum по `discovery_data + 0x38` проходит проверку
  discovery type. Та же структура затем добавляется во внутреннее хранилище и
  передаётся observers.
- Функция уведомлений после кандидата выбирает `DISC_CREATURES`, `DISC_FLORA`
  и `DISC_MINERALS` по тому же enum. Это подтверждает значения `3`, `4`, `5`
  для интересующих типов в данном runtime-пути.
- Три hook-сигнатуры, нужные внутреннему loader NMS.py, также имеют по одному
  совпадению в `NMS.exe` 178938.
- PDB для конкретного `NMS.exe` локально отсутствует, поэтому исходное
  символьное имя VA `0x14044EB60` не подтверждено.
- Сигнатура `cGcScanManager::UpdateScannableMarkers` имеет одно совпадение:
  VA `0x1412EFF00`, file offset `0x12EF300`.
- Функция обходит vector по `cGcScanManager + 0x22F0`. В build `178938`
  размер одного `cGcMarkerPoint` равен `0x2B0`, тогда как установленный NMS.py
  всё ещё объявляет устаревший размер `0x270`.
- Для текущего marker record подтверждены: `mNode +0x124`, `mModelNode +0x128`,
  `mEntranceNode +0x12C`, marker type `+0x291` и bitfields `+0x2AB/+0x2AC`.
  Старый offset marker type из NMS.py `+0x25B` для этого build неприменим.

## Подтверждено первым runtime-запуском

- Игра запустилась через `run.ps1`, однако файл `pymhf-*.log` не появился.
- pyMHF создал cache сигнатур NMS в `%APPDATA%\pymhf\nmspy\.cache`; в нём
  присутствуют адреса обеих точек наблюдения, но это ещё не доказывает вызов hooks.
- Живая диагностика второго запуска показала, что probe был загружен, failed
  hooks отсутствовали, но effective config всё ещё содержал
  `logging.shown = true`, `log_dir = "{EXE_DIR}"` и активный `SocketHandler`.
- Причиной оказалась Windows package virtualization: Codex Desktop видел
  `%APPDATA%` через `OpenAI.Codex_*\LocalCache\Roaming`, тогда как обычный
  PowerShell и NMS читали физический `%USERPROFILE%\AppData\Roaming`.
- Настоящий TOML содержал только `mod_dir`. Во время второго запуска к живому
  процессу подключён прямой `FileHandler`, после чего логирование подтверждено.
  Физический TOML также обновлён: `logging.shown = false` и проектный `log_dir`
  будут использоваться на следующих запусках.
- Windows PowerShell 5.1 прочитал исходные UTF-8 без BOM скрипты как системную
  однобайтовую кодировку, из-за чего русские строковые литералы превратились в
  синтаксические ошибки. Все `.ps1` переведены в UTF-8 with BOM и успешно
  проверены парсером Windows PowerShell 5.1 и PowerShell 7.

## Рабочие гипотезы

- VA `0x14044EB60` — изменённая в NMS 7.0.x реализация функции, эквивалентной
  `cGcDiscoveryManager::SubmitDiscoveryData`. Runtime milestone подтверждает её
  поведение, но точное символьное имя требует PDB.
- Offset типа `0x40` из текущего объявления NMS.py устарел для наблюдаемой
  структуры build `178938`; в этом пути подтверждён offset `0x38`.

## Следующая проверка

Этап 1 завершён, пользователь отдельно разрешил этап 2. В ветке
`experiment/stage2-submit-override` подготовлена следующая рабочая гипотеза:
для наведённого неизвестного объекта одноразовая подмена только
`submit=False` на `True` может запустить штатный pipeline регистрации.

Эксперимент подтверждён runtime-логом и изменением экранного счётчика. F8 на
отпускании вооружает только следующий подходящий вызов; после первой активации
повторные F8 игнорируются до перезапуска.

Первая попытка этапа 2 не выполнила подмену: F8 вооружил sequence 1, но при
неподвижном наведении новый `PopulateDiscoveryInfo` не пришёл. Следующий вызов
появился через 10,478 секунды и только тогда зафиксировал истечение исходного
трёхсекундного окна. `Stage2SubmitOverride` и связанного submit не было,
счётчик остался `8/26`; сохранение не изменилось. Это подтверждает, что для
эксперимента нужно вооружиться вне цели, а затем вызвать повторный target
acquisition. Окно увеличено до 10 секунд, нулевая цель его не расходует.

Вторая попытка этапа 2 выполнила именно запланированную подмену:

- `23:30:48.637`: `Stage2OverrideArmed`, sequence 1, окно 10 секунд;
- `23:30:53.255`: следующий подходящий `PopulateDiscoveryInfo` пришёл с
  `submit=False`, а effective argument стал `submit=True`;
- тот же вызов имел UA `4747691344427360`, тип `5` (`Mineral`);
- штатный `SubmitDiscoveryDataV70Candidate` вернул `result=True`;
- визуально объект автоматически завершил сканирование без удержания обычной
  кнопки сканирования (со слов пользователя).

После отката сохранения без завершения процесса NMS последующие F8 закономерно
логировались как `Stage2OverrideArmIgnored: attempt_already_started`: одноразовый
предохранитель относится к процессу игры, а не к загруженному сохранению.
В контрольном повторе `23:39:05.953` F8 вооружил подмену, а в
`23:39:14.853` неизвестный минерал снова прошёл путь `submit=False -> True`.
Submit-кандидат получил UA `4747691344427360`, тип `Mineral` и вернул
`result=True`. Пользователь подтвердил, что экранный счётчик изменился и объект
был зарегистрирован без обычного сканирования. Второй минерал не регистрировался:
это ожидаемое действие одноразового ограничения этапа 2.

Этап 2 завершён. Для первого эксперимента этапа 3 выбран общий marker vector
`cGcScanManager + 0x22F0`. F8 dry-run только читает один bounded snapshot после
штатного `UpdateScannableMarkers` и сопоставляет три handle каждого marker record
с последним `target_node`, замеченным в `PopulateDiscoveryInfo`.

Рабочая гипотеза: хотя vector содержит не только открытия, в нём присутствует
наведённый discovery target. До runtime-сопоставления это не подтверждено. Даже
при совпадении потребуется найти безопасный путь от marker record к валидному
target attachment; один node handle ещё недостаточен для массовой регистрации.

Runtime-проверка этапа 3 (`pymhf-20260914T000415.log`) опровергла эту гипотезу:

- F8 запросил ровно один read-only snapshot; ошибок hooks и исключений не было;
- vector имел `capacity=29`, `size=26`, `read_count=26`, `truncated=False`;
- 17 записей содержали валидные node handles, а типы и значения выглядели
  согласованно: 15 `Object`, два `TerrainResource`, `Ship`, `PlayerBase`,
  четыре полюса и другие HUD/POI markers;
- активный неизвестный минерал имел `target_node=0x29B37A`, но ни `mNode`, ни
  `mModelNode`, ни `mEntranceNode` одной из 26 записей с ним не совпали;
- итог snapshot: `target_matches=0`.

Следовательно, `cGcScanManager + 0x22F0` действительно декодирован как marker
vector текущего build, но это общий список HUD/POI-маркеров, а не реестр
загруженных discovery targets. Его нельзя использовать как источник объектов
для массовой регистрации. Сохранение на этапе 3 не изменялось.

## Подготовка этапа 4

MSVC RTTI в `NMS.exe` содержит `cGcScannableComponent` и специализированный
`cTkComponentPoolInterfaceT<cGcScannableComponent>`. Через complete object
locator подтверждён vtable `VA 0x144AB61D0` (`RVA 0x4AB61D0`). Первый virtual
function — destructor `VA 0x1410ECF60`; он освобождает объект размером `0x330`.

Второй virtual function `VA 0x1410ED370` является update компонента. Он читает
`cGcScannableComponentData`, проверяет дальность и состояние, а затем добавляет
embedded marker через уже подтверждённый `TryAddMarker` (`VA 0x1412BB8A0`) или
удаляет его. В текущем build подтверждены следующие поля компонента:

- data pointer `+0x28`, node handle `+0x38`, component flags `+0x1F`;
- embedded marker начинается по `+0x40`, marker type находится по `+0x2D1`;
- флаг присутствия marker по `+0x320`, полный размер компонента `0x330`.

Оба прямых caller этой update-функции раскрывают глобальный component pool:
bucket count `RVA 0x71A8354`, pointer на массив buckets `RVA 0x71A8358`, число
slots на bucket `RVA 0x70FE294`. Slot имеет размер `0x10`: pointer компонента по
`+0x0` и active byte по `+0x8`.

Рабочая гипотеза этапа 4: bounded read-only обход этого специализированного
пула содержит настоящий `cGcScannableComponent` наведённого неизвестного
минерала. Проверка сопоставит node/attachment с последним
`PopulateDiscoveryInfo`; никакие поля и игровые функции не изменяются.

## Результат этапа 4 и подготовка этапа 5

Runtime-проверка этапа 4 (`pymhf-20260914T033953.log`) опровергла точную
гипотезу о пуле `cGcScannableComponent`, но подтвердила корректность его layout:

- один bucket, 321 slot, 63 active slot;
- все 63 объекта имели точный vtable `cGcScannableComponent`, ошибок чтения и
  vtable mismatch не было;
- все имели `ScannableType=Binoculars`, но почти все относились к обычным
  markers/interactables; из discovery-типов были только две hazard flora;
- неизвестный минерал `target_node=0x29B512` отсутствовал, `target_matches=0`
  в обоих снимках.

Статическая декомпиляция показала более общий путь. В начале
`PopulateDiscoveryInfo` функция `VA 0x140448DC0` принимает scene-node handle,
текущий planet address и выходной `cGcDiscoveryData`. Она возвращает `bool` и
заполняет тип по `+0x38`; у неё 11 прямых caller в текущем build.

Функция движка по `VA 0x1418366E0` раскрыла актуальный `cEgSceneNodeData`:

- глобальный pointer `RVA 0x6E13DC8`;
- node pointer buffer `+0x90`, status buffer `+0xA0`;
- handle-to-dense-index buffer `+0xE8`, generation buffer `+0xF0`;
- lookup использует младшие 19 бит handle, generation — старшие биты.

Во время ещё работающего процесса выполнено внешнее read-only чтение памяти.
Последний минерал найден точно:

```text
target_handle=0x29B512
lookup=0x1B512
dense_index=38572
stored_handle=0x29B512
exact_match=True
status=2
```

Из функции absolute transform (`VA 0x141833580`) подтверждены transform buffer
`+0x60`, stride `0x40` и position `+0x30`. В живой таблице было 4557 записей со
status 2; в радиусе 100 метров от минерала — 662. Поэтому этап 5 ограниченно
вызывает resolver максимум для 1024 ближайших живых узлов, дедуплицирует
полученные discovery data и только логирует результат. Submit отключён.

## Результат этапа 5

Runtime-проверка этапа 5 (`pymhf-20260914T040624.log`) полностью подтвердила
связку общей таблицы scene nodes со штатным discovery resolver:

- F8 был запрошен в `04:07:37.576`, bounded snapshot завершился в
  `04:07:41.436` без исключений;
- целевой минерал `0x29B8DE` прошёл generation/status/stored-handle проверки и
  resolver вернул для него `type=5`, правильный universe address и два ключа;
- `target_resolved=True`, submit оставался отключён;
- в радиусе 100 метров оказалось 128 точных живых scene-node кандидатов;
- resolver вернул success для 22, из них 19 относились к Animal/Flora/Mineral;
- диагностическая дедупликация всех заполненных ключей дала 11 записей:
  6 Animal, 4 Flora и 1 Mineral;
- два scene node целевого минерала имели один fingerprint, а повторные узлы
  флоры и фауны также корректно схлопнулись по discovery keys;
- после F8 вызовов submit-кандидата не было, сохранение этим dry-run не менялось.

Таким образом, обе недостающие части будущего массового сканера подтверждены
runtime: nearby discovery можно перечислить через scene-node table, а валидный
`cGcDiscoveryData` можно передать уже проверенному submit pipeline. Следующий
этап должен отдельно и явно разрешить mutation, дедуплицировать до submit и
ограничить один F8 одним проходом.

Дополнительная декомпиляция submit-кандидата уточнила его identity comparator:
он хеширует и сравнивает максимум первые три discovery keys, даже когда fauna
data содержит четыре или пять. Поэтому две пары записей Animal из этапа 5 были
вариантами тех же видов; submit-эквивалентный итог снимка равен 9 уникальным
видам: 4 Animal, 4 Flora и 1 Mineral. Этап 6 использует именно это правило.

Для точного повторения штатного пути этапа 6 также подтверждены:

- discovery manager по `game_state + 0x2CE840`;
- `_time64(nullptr)` trampoline `VA 0x142BEFC70`;
- проверка уже известного discovery `VA 0x1412334B0`;
- post-submit обработка `VA 0x140511560`, которую `PopulateDiscoveryInfo`
  вызывает только когда submit вернул true или установил `locally_new`.

Mutation этапа 6 ограничен одним F8 на процесс, 100 метрами, 1024 resolver calls
и 32 уникальными submit. Уже известные discovery пропускаются до submit.

## Этап 6: первый mutation runtime

В запуске `20260914T041921` F8 построил снимок из 376 nearby candidates.
Resolver успешно обработал 39 узлов и выделил 7 уникальных discovery: 4 Animal
и 3 Mineral. Все четыре Animal уже были известны, а штатный submit вернул
`True` для каждого из трёх неизвестных Mineral; post-submit также был вызван
трижды. Однако игровой счётчик визуально увеличился только на два минерала и
уведомления не появились. Все три вызова произошли в одну миллисекунду, поэтому
этап 6.1 отправляет очередь по одному discovery с интервалом в секунду.

В следующем свежем процессе F8 был корректно проигнорирован с
`reason=no_valid_target`: до нажатия не произошло ни одного
`PopulateDiscoveryInfo`, поэтому валидный scene-node handle ещё не был захвачен.
Такой отказ не расходует одноразовую попытку.

## Этап 6.1: paced submit подтверждён счётчиками

В запуске `20260914T044053` снимок радиуса 100 метров содержал 385 точных
живых scene nodes. Resolver успешно обработал 38 узлов и получил 6 уникальных
discovery: 3 Animal, 2 Flora и 1 Mineral. Все Animal уже были известны.

Очередь из трёх неизвестных объектов была отправлена с интервалом в секунду:

- item 1: Mineral, `result=True`;
- item 2: Flora, `result=True`;
- item 3: Flora, `result=True`.

Итог лога `accepted_type_counts=Flora:2,Mineral:1` точно совпал с наблюдаемым
изменением игровых счётчиков: `+2 Flora` и `+1 Mineral`. Это первый runtime-тест,
который подтверждает loaded-area scanner не только возвратом функции, но и
реальным прогрессом Discoveries. Штатные экранные уведомления при таком вызове
не появились; пользователь решил не считать их обязательными.

## Этап 6.2: повторные проходы подтверждены

В запуске `20260914T044958` один процесс успешно выполнил четыре независимых
прохода F8. Они приняли соответственно 3, 3, 1 и 1 новое discovery без ошибок.
Первые два прохода дали по `Flora:2,Mineral:1`; третий — `Flora:1`, четвёртый —
`Mineral:1`. Это подтверждает снятие одноразового ограничения и корректную
штатную фильтрацию уже известных видов между проходами.

Несколько F8 без активного визора были ожидаемо отклонены с
`reason=no_recent_valid_target`. Это ограничение относится только к выбору
геометрического центра; submit pipeline от визора не зависит.

## Player-centred anchor и HUD-уведомления

Установленная NMS.py описывает путь `cGcApplication::Data + 0x4CCF90` к
`cGcSimulation`, затем `+0xAC8B0` к `cGcEnvironment`, `+0x8C0` к
`cGcPlayerEnvironment` и `+0x30` к позиции `mPlayerTM`. Read-only проверка в
живом процессе вернула позицию игрока
`(-713.300,-3738.549,130458.805)`. Последняя цель визора имела позицию
`(-710.633,-3739.398,130451.500)`, то есть находилась примерно в восьми метрах.
Цепочка пригодна для F8 без визора и без target scene-node.

Декомпиляция `PopulateDiscoveryInfo` показывает, что после успешных submit и
`FUN_140511560` штатный путь при `silent=False` отдельно записывает состояние в
переданный `DiscoveryInfo` и создаёт/настраивает связанную HUD-сущность. Массовый
путь вызывает post-submit, поэтому слышен звук, но у него нет экземпляра
`DiscoveryInfo` для каждой удалённой scene node; поэтому карточки уведомлений не
появляются. Воспроизведение HUD-части требует отдельного эксперимента и не нужно
для изменения счётчиков Discoveries.

## Этап 7: player-centred wide pass и граница loaded-area

Радиус прохода увеличен до 1000 метров, лимит resolver calls — до 4096, а
геометрический центр берётся напрямую из позиции игрока. F8 больше не требует
активного визора или наведённой цели. Runtime подтвердил повторные проходы и
массовое добавление Flora/Mineral, но также показал принципиальную границу:
resolver может обработать только уже созданные scene nodes. Визуально близкий
объект иногда уже известен в каталоге, хотя его конкретный экземпляр ещё
выглядит несканированным; ожидание после прохода эту разницу не устраняет.

## Полная fauna без живых scene nodes

В `cGcPlanetData::SpawnData.Creatures` хранится полный массив
`cGcCreatureSpawnData` для планеты. Он существует независимо от появления
животных рядом с игроком и содержит все данные, необходимые для построения
четырёх discovery keys типа Animal.

Декомпиляция `FUN_141208F90` и сопоставление с шестью видами, реально
полученными через `PopulateDiscoveryInfo`, дали точную формулу:

1. `key[0]` — unsigned 64-bit значение `cGcCreatureRoleData::Seed`;
2. `key[1]` — DJB2-64 (`initial=0x1505`, `hash=hash*33+byte`) от uppercase
   пути `Resource.Filename`;
3. `key[2]` — внутренний 64-bit mixer сначала от двух qword строки
   `CreatureID`, затем от результата и `Seed`;
4. `key[3]` — тот же mixer последовательно от universe address планеты,
   `CreatureType` и `cGcCreatureInfo::Rarity` из соответствующей роли.

Внутренний mixer для пары `(a, b)` использует константу
`0x9DDFEA08EB382D69` и unsigned 64-bit переполнение:

```text
x = (a ^ b) * C
y = ((x >> 47) ^ x ^ a) * C
mix(a, b) = ((y >> 47) ^ y) * C
```

Для ANTELOPE, TWOLEGANTELOPE, COW, GRUNT, CAT и BIRD все четыре вычисленных
ключа совпали с resolver бит-в-бит. Например, первый ключ каждого из этих
видов равен его role seed, а второй ключ точно совпадает с DJB2-64 пути модели.
Дополнительно lookup уже известного BIRD в новой системе вернул сохранённый
`key[3]`, который точно совпал с `mix(mix(UA, CreatureType), Info.Rarity)`.
Это устраняет зависимость полной fauna от радиуса и наличия живых животных.
Следующий безопасный этап — catalog dry-run: сгенерировать все Animal записи
текущей планеты, сравнить их с resolver-результатами и только после контрольной
проверки подключить их к paced submit.

## Этап 8: полная fauna подтверждена интерфейсом

Первый runtime-запуск полного каталога успешно обработал две разные планеты.
На первой `PlanetFaunaCatalogReady` нашёл 17 видов: 10 из них одновременно
присутствовали среди живых scene nodes и все 10 совпали с вычисленными
fingerprint. В очередь вошли все 17 неизвестных Animal, и штатный pipeline
принял все 17. На второй планете каталог содержал 6 видов, три resolver-match;
все 6 Animal также были приняты. Пользователь подтвердил полные счётчики фауны
в интерфейсе игры.

Те же проходы зарегистрировали только загруженные Flora/Mineral:
`Flora:2,Mineral:4` на первой планете и `Flora:4,Mineral:2` на второй. Это
подтверждает, что planet-catalog метод пока применяется только к Animal.

Заметный стоп-кадр относится главным образом к старому scene-node снимку:
между F8 и `SceneResolverSnapshotBegin` прошло 6.4 секунды на первом проходе и
12.0 секунды на втором. Причина — синхронный обход фиксированной таблицы из
524288 handle slots и чтение больших буферов в игровом потоке. Полный Animal
catalog не требует этого обхода; для публичной версии loaded-area обработку
следует выполнять порциями между кадрами либо вынести на отдельную клавишу.

## Этап 9: полный планетарный каталог подтверждён

`cTkResourceManager::mResources` содержит загруженные записи всех процедурно
выбранных scene-ресурсов текущей планеты, включая ещё не созданные scene nodes.
Для Flora и Mineral discovery identity восстанавливается непосредственно из
`cTkResource`: `key[0]` равен descriptor seed, `key[1]` — DJB2-64 uppercase
пути `.SCENE.MBIN`, а тип определяется статическим каталогом scene-path hashes.

Каталог построен из всех игровых external object lists для NMS 7.0 и содержит
192 Flora и 188 Mineral scene hashes без пересечений. В runtime ресурсы текущей
планеты образуют компактный кластер; выбирается кластер с наибольшим числом
активных ссылок, при этом редкие entries с `refcount == 1` не теряются. Полная
fauna из этапа 8 объединяется с этим каталогом до штатной known-проверки.

Подтверждены два полных прохода:

- первый: 78 210 ресурсов, 151 совпадение, 19 planet-object entries и 7 Animal;
  каталог собран за 0.551 с, 23 неизвестных из 26 приняты полностью —
  `Animal:6, Flora:6, Mineral:11`;
- второй: 78 949 ресурсов, 159 совпадений, 42 planet-object entries и 14 Animal;
  каталог собран за 0.742 с, все 56 неизвестных приняты —
  `Animal:14, Flora:24, Mineral:18`.

Пользователь подтвердил полные игровые счётчики на обеих планетах. Старый обход
524 288 scene-node slots полностью удалён из F8 path, поэтому каталог строится
без прежнего многосекундного стоп-кадра. Множество звуков на богатой планете
соответствует числу принятых entries: paced queue намеренно вызывает один
штатный post-submit в секунду.

`PostSubmitDiscovery` вызывается с `silent=False`; декомпиляция подтверждает
обычный расчёт награды и ветви `BIG_SCAN_CRE`, `BIG_SCAN_PLA`, `BIG_SCAN_MIN`.
Большая карточка нового объекта, однако, создаётся позже в
`PopulateDiscoveryInfo` из живого `DiscoveryInfo` и связанной scene/HUD entity.
У удалённых planet-catalog entries таких экземпляров нет. Их фабрикация для
десятков записей признана несоразмерно рискованной и исключена из релиза 1.0.

## Этап 9.1: spawn-массивы планеты вместо кластера ресурсов

Кластер `mResources` оказался эвристикой: на планете UA 4561877911412995 он
дал `Minerals 17/18`, а на UA 18072676793524483 захватил только часть Flora и
Mineral. Точный источник — три spawn-массива inline-планеты `cGcSolarSystem`
(`planet+0x3C08/+0x3C18/+0x3C28`, `{u32 capacity, u32 size}` перед указателем,
элемент `0x70`: filename `+0x18`, seed `+0x38`, use-seed `+0x40`). Read-only
чтение живого процесса воспроизвело знаменатели игры: 32 Flora / 18 Mineral на
первой планете и ровно 23 Mineral на второй; все save records второй планеты
лежат внутри каталога. Flora второй планеты — надмножество (26 против 21 в
квесте), лишние records на счётчик не влияют.

Две ошибки статического классификатора подтверждены save/resolver:
`STEAMVENT` (Mineral только через `ScanIcon` дочерней `GEM.ENTITY`) игрой не
засчитывается, а `FISHFIENDROCK` (вложенная scene без прямого entity) является
Mineral по штатному resolver и входит в знаменатель. Обе исправлены явными
overrides в генераторе. Подробности и runtime-протокол — `docs/HANDOFF.md`.
